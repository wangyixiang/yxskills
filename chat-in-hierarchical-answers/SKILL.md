# Chat in Hierarchical Answers（分级缩进式回答）

## 核心目标

让回答本身可以按深度阅读：只读外层就拿到结论和主干；每多读一层，得到更具体的展开；在任何一层停下，都不缺核心信息。

多数传统提纲的父级只是分类标签（“背景”“方案”“结论”），读者必须读完整节才知道说了什么。这里的要求相反：**父级行本身携带信息，是下一层内容的压缩表达。**

## 适用范围

只作用于**对话中的回答**。

- 不用于：文档、报告、README、邮件、代码注释、提交信息、PR 描述、生成的文件内容。
- 当回答本身就是交付物时（如“写成文档”“生成报告”），按该交付物自己的格式组织，不用本技能。
- 明显不适用时直接正常回答，不要硬套层级：一个词或一句话就能说清的事实、纯代码、数学推导、直接引用、翻译、简单确认（“已完成”）、纯表格数据。

## 格式规则

1. 用 Markdown 嵌套列表表达层级，通常 2–4 层；层级深度由内容决定，不为了好看凑层。
2. 除最内层外，每条父级文字要概括其直接子项的核心信息；子项之间是并列展开。
3. 父级应是能独立成立的完整判断或结论，不是“原因”“建议”“细节”这类空标签。
4. 子级必须增加新信息：证据、步骤、例子、数字、边界条件；不要换句话复述父级。
5. 同一层的条目保持平行：同一抽象层级、相近的句式和长度。
6. 每层通常不超过 5–7 条；超出时换个分法，而不是继续堆。
7. 根层给出整段回答的总判断；只读根层也应知道答案是什么。
8. 关键结论不要只藏在最内层；最内层只放不可再压缩的具体信息。
9. 分层不等于变长。若分层后信息没有增加，压回一两句话。

## 写作方法

1. 先想清楚答案的金字塔：总判断 → 2–4 个支撑论点 → 每个论点的证据或细节。
2. 自上而下写：先把父级写成一句包含结论的话，再展开子级。
3. 遮住子级自检：父级是否仍然信息完整、可以独立阅读？若只是标签，重写父级。
4. 检查停顿点：读者停在第 1 层、第 2 层、最内层，是否都能得到该层应有的完整信息？

## 发送前自检

- 根层是否直接给出了总判断？
- 每个非最内层能否脱离子级独立成立？
- 是否存在“背景 / 方案 / 结论”这类纯标签父级？
- 读者停在任意深度，是否都不丢核心信息？
- 是否误用在了文档或文件输出中？

## 停止与恢复

本技能默认在对话中持续生效，但用户始终掌握开关。

- 停止口令：用户说“不用分层了”“正常回答”“别再缩进了”“用散文说”“关掉分级回答”“stop hierarchical answers”等任何明确的停止要求，立即停止。
  - 从该条消息起，当前会话内后续回答全部恢复普通格式，不要只改一句又在下一轮自动恢复。
  - 不需要用户解释原因，也不要追问“确定吗”。
- 恢复方式：只有用户明确说“恢复分级回答”“重新用分层缩进”“继续用提纲”等，才重新启用。
- 区分单次例外和整体停止：用户说“这条用一句话说”“这里别分层”只影响当前回答；说“以后都正常回答”“别再用这个格式”则整体停止，直到用户明确要求恢复。
- 用户反复要求“更自然”“更短”“不要提纲”或表达不满时，按停止信号处理，不必等精确口令。
- 彻底卸载：如果用户想在所有对话中永久停用，告诉对方把技能目录从发现路径移除或删除（如 `~/.agents/skills/chat-in-hierarchical-answers/`，或项目内 `.agents/skills/`、`.zcode/skills/` 下的同名目录）；当前会话内则可以先用停止口令。
- 用户问“怎么停用这个技能”时，直接按上面两条回答：会话内用停止口令，永久停用则移除技能目录。

## 边界

- 用户明确要求散文、公文、信件等文体时，遵从用户，不用缩进提纲。
- 一两句话能答完时不必强行分层。
- 代码块、公式、引用保持原样，不要塞进缩进层级里假装是论点。
